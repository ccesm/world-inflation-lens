# V0.11 — Homepage layout repair and daily notifications

## Reproduced bug and fix

The homepage framework had seven cards but a desktop grid hard-coded for six cards with narrow separator columns. At 1440 pixels the seventh card occupied a roughly 30-pixel column and became over 1100 pixels tall. The earlier small-screen checks did not cover this wide-screen failure.

Cards are now the only grid items; decorative plus signs belong inside cards. A responsive equal-width grid wraps based on available space and no longer depends on the number of forces. All seven forces, links and methodology remain. Before/after browser measurements showed the seventh card change from 30 pixels to approximately 291 pixels wide at the same desktop viewport.

The daily-check health threshold is now 48 hours (previously ten days). Invalid or future check timestamps are also marked overdue instead of appearing healthy.

## Daily official-source updates

The existing GitHub Pages workflow now runs every day at **08:00 America/Los_Angeles**. GitHub's timezone-aware schedule handles daylight saving time. Runs may be delayed; this is a scheduled check, not a guarantee of exact-time data delivery. See [GitHub schedule documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

The task checks the existing official/public endpoints and publishes only after full validation, build and verification. Original monthly/quarterly/annual frequencies remain unchanged. CBO projections, SIPRI annual releases and manually reviewed stablecoin publication estimates retain their reviewed versions. This task does not scrape general news or generate macro forecasts.

The original atomic snapshot replacement, revision ledger and rollback are retained. Pushes to main still deploy without fetching data. Manual workflow dispatch with `refresh: true` performs an immediate data check and notification. The workflow's time budget is raised to 30 minutes to accommodate source retries.

## Email reminders — setup required

The sending implementation uses [Resend's email API](https://resend.com/docs/api-reference/emails/send-email) from the GitHub runner. No mail credentials are bundled in the frontend, and no new dependency is needed. Resend is the implementation default pending the user's preferred provider.

Configure these **repository Actions secrets**:

| Secret | Meaning |
| --- | --- |
| `RESEND_API_KEY` | Sending key from the user's Resend account |
| `NOTIFY_FROM` | Single plain sender email address on a verified sending domain |
| `NOTIFY_TO` | Single recipient email address chosen by the user |

Set them in GitHub repository → Settings → Secrets and variables → Actions. Do not put them in source files, `VITE_` variables, issue comments or chat. The project does not create a Resend account, buy a service, assume a recipient, or modify DNS automatically.

Mail runs after both build and deployment for daily checks and refresh-enabled manual runs. Normal code pushes do not send mail. The mail job checks out the precise snapshot commit used by the build. It distinguishes successful deployment with changed observations, a successful unchanged check, and incomplete updates/deployment. A ledger entry must match the current GitHub run ID to support a success claim. An old successful record cannot be presented as today's result.

The bilingual plain-text digest includes revision counts, a few source-specific latest observation dates and units, and links to the website and current run. Failure notices explicitly avoid new-data claims. Addresses and keys are not logged. Transient request failures retry at most three times using the same idempotency key and payload. Resend acceptance is reported as acceptance, not confirmed inbox delivery. A deliberate workflow rerun is a new attempt and can send another notice; provider deduplication lasts 24 hours.

When secrets are absent, the job clearly warns **email not sent** and leaves data deployment available. No email has been sent during development. End-to-end delivery cannot be verified until the recipient and sender credentials are configured.

`npm run notify:preview` renders a safe preview without reading mail configuration or making a sending request. With no workflow context it intentionally demonstrates the incomplete-run notice. Unit tests separately exercise successful and unchanged results with fixtures.
